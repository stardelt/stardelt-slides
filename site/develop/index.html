Develop on stardelt

Write, publish, schedule, watch. Ship through Git.

A deck for developers: where your code runs, how a notebook is published and scheduled, and how work moves from dev to prod through Git. Every slide follows one section of the developer guide and the two notebook guides. The last slide is the live demo, in five steps.

Three ways to work, and all of them run as you: the kernel and every query use your platform identity. The browser is JupyterLab, started from Nova's Notebooks page. VS Code connects either to your workspace, which is the full platform with Spark and table writes, or to a local kernel after stardelt login, where only queries leave the laptop.

A notebook from write to watch

Write the notebook in JupyterLab in your workspace, and publish it with the toolbar button or the command line. Then schedule the pinned version in Nova and watch its runs there. A failed run opens the executed notebook at the cell that failed.

Publish

import stardelt
stardelt.publish("daily_trips.ipynb")

stardelt notebook publish daily_trips.ipynb --group analytics

Every publish stores a new immutable version.

The same publish from a cell in the file's directory, or from a laptop after stardelt login. The call sends the file to the notebook API and prints the name, the group, the version, its sha256 and the parameters it found. Publishing the same bytes again stores nothing and answers the existing version.

Mark the parameters cell

Tag one cell parameters and write one name = literal line per parameter. Nova reads the lines of the first cell carrying that tag, in order, at most 32.

In JupyterLab, right-click the cell and choose Mark as parameters cell; the same again removes the tag. Nova reads the lines of the first cell carrying the tag, at most 32, and the first occurrence of a name wins. Defaults stay text and are never evaluated, so a default cannot run code.

Schedule a version

  • Schedule the newest version from a row, or schedule this version from a version's row.
  • The dialog asks for a name, a group, parameters and a clock.
  • Runs as the group's principal, not as you.

The schedule pins the version it was created with.

Schedule the newest version from the notebook's row, or pin one version from its own row on the notebook page. Each edit can pin another version; in edit mode the list also offers the newest. The run uses the group's principal pipeline-<group>, so it reaches exactly what the group may reach, not what you personally may.

Watch it run

Open a run to see the executed notebook, opened at the cell that failed.

Build → Runs lists every run of the notebooks and pipelines your groups own, filterable by kind, state and group. Open a run to see its tasks, the task log and the executed notebook. A failed run opens at the cell that failed and names the exception above the notebook.

From dev to prod

The second part: how a team's work moves from a development stage to production. Four steps, and Git carries the work between them.

Ship through Git

Describe

A bundle in Git says what the team publishes, with one target per stage.

Try in dev

Deploy to your own development stage, where pipelines are named dev-<you>-<name> and nothing is scheduled.

Review in a pull request

Validate needs nothing from the cluster; plan asks Nova and writes nothing.

Publish to production

Deploy writes only when Nova accepts every pipeline, and stamps each with its commit.

A bundle is a directory in Git: the pipeline files, the SQL and notebooks they read, and one target per stage. validate checks what needs no cluster, plan asks Nova what a deploy would do and writes nothing, and deploy writes only when Nova accepts every pipeline. A production pipeline is stamped with the bundle, the target and the commit, so a deploy can be traced back to a change.

Build once, deploy many

A stage never copies objects to another stage: Git carries them. Each pipeline is stamped with where it came from, the target and the Git commit. To go back to an earlier state, check out the earlier commit and deploy again.

Keep notebooks thin

Logic belongs in .py modules with pytest tests, where it is reviewable and testable without a kernel.

A module is reviewable and testable without a kernel, so the notebook only calls it and shows the result. A rerun is then cheap, and a failure names a line of code instead of a cell. The tests run in CI like any other test.
