Three ways in, in the order of least effort: use it and report what went wrong, fix a page, or take a whole issue. Installing and reporting is the most useful thing a newcomer can do, because the maintainers can no longer see their own documentation. On an issue, comment "claiming" so nobody builds it twice.

Six repositories: docs, platform, the interface and API, the operator, the Python package and the sample pipelines. Each one has a single check to run before a pull request, listed in the guide. Paste the command and its result into the description.

The two rules

Rule one

Everything arrives as a pull request.

main is protected.

Rule two

main stays installable.

There are no tagged releases yet, so people install from it.

Two rules hold everywhere, and everything else in the guide follows from them. main is protected, so a change arrives as a pull request and never as a push. And because there are no tagged releases yet, whatever lands on main is what people install.

What a reviewer asks

One

Does it do what the description says, no more and no less?

Two

Does it change something a user or operator can see? Does it say so?

Three

Is there evidence that it works?

Four

Does it fit the rules and the license policy?

Expect one maintainer review, about correctness rather than style. A reviewer asks these four questions, so answer them in the pull request before they are asked. There is no fixed response time: ping a pull request that has been quiet for a week.

AI assistants are welcome.

Name the model in the description, so a reviewer knows what to check more closely — and you are the author.

Assistants are welcome on two conditions. Name the model in the description, or as a Model trailer naming the provider and the model. And you are the author: run the checks yourself and answer the review yourself, because a green transcript is not evidence.

An issue anyone can build

Name the file and symbol

Name the file, symbol and line, never "the controller".

Give the exact command and its output

"It works" cannot be checked.

One issue, one pull request

Up to about 150 lines, because small changes get merged.

An issue is ready when someone who has never seen the repository can do the work without asking a question. That means naming the file, symbol and line, giving the exact command and its expected output, and keeping one issue to one pull request. Run every command yourself before you paste it, so the issue cannot teach people to improvise.
