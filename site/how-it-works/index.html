How stardelt works

One front door, open engines, plugs instead of a monolith.

One picture of the whole platform: who talks to what, and why. Dashed boxes are optional or switch on per install.

The whole platform in one picture

Read it from the top: people and tools, Nova, engines, catalog, storage, control plane.

Read the picture from the top. People and tools sign in once and talk to one front door, stardelt Nova. Nova asks the engines and the catalog on their behalf, table files live in storage, and the control plane runs on the Kubernetes cluster you bring.
01

From the top

Six boxes from the top of the picture, two slides of three. Each box is one layer of the platform and names its parts.

1

You and your tools

A person works in the browser (the Nova interface), a script or a CI job uses the stardelt command line or the Python package, an AI assistant uses the local MCP server, a notebook runs in JupyterHub. All of them sign in once.

2

One front door: Nova

The interface and the public API are the same thing: the command line, the Python package and the MCP tools are generated from the one OpenAPI contract Nova publishes (/api/openapi.json, described in the API reference).

3

Engines and apps

Trino answers SQL. Airflow runs scheduled pipelines and sends their SQL to Trino. Superset draws dashboards from Trino. Spark Connect takes the heavy jobs.

The top of the picture: people and their tools, the one front door, and the engines behind it. A feature that exists in the interface exists in the API. Nova asks the engines for you; notebooks talk to them directly with your token.

4

Catalog and access

Lakekeeper is the Iceberg catalog: it knows which tables exist and which files belong to them, and every engine asks it first. OpenFGA, when it is on, decides who may see which table.

5

Storage

Tables are open Iceberg files (Parquet) in SeaweedFS, or in your own S3. Nothing is locked into a stardelt format.

6

Control plane

The stardelt Operator reads small resources (PlatformInstance, Lakehouse, Connection, ServicePrincipal and StreamApp) and installs and wires the services above.

The bottom of the picture: the catalog every engine asks first, the storage the tables live in, and the control plane that installs and wires the rest. CloudNativePG keeps the Postgres databases; ingress-nginx and cert-manager give every service its HTTPS name. All of it runs on a Kubernetes cluster you bring.
02

Five things to remember

Five sentences to take away from the picture. They are the claims the next two slides unpack.

One sign-in

The OIDC provider you already run holds users and groups; small installs can start with the bundled Keycloak.

One API

Whatever you can click, you can call.

Nova acts as you

With sign-in on, your token goes on to the engines, so what you may read is decided by the engine and the catalog for you, not by Nova's own power.

One sign-in: the browser uses the sign-in page, the command line uses the device code flow, and the same token reaches the engines. One API: whatever you can click, you can call. Nova acts as you, so permissions are enforced by the engine and the catalog.

Plugs, not a monolith

The engine, the catalog, the identity provider and the object store are replaceable behind open contracts (SQL, the Iceberg REST catalog, OIDC, S3).

Known limits

Results Nova keeps in memory are capped (100 000 rows or about 64 MiB per statement); storage credentials are one platform key today, not yet one short-lived key per person.

Plugs, not a monolith: the engine, the catalog, the identity provider and the object store are replaceable behind open contracts. The known limits are the in-memory result cap and one platform storage key. Say both plainly; the audience will ask about the second.
03

Where each task is done

The picture answers where things run; this part answers where work is done. Four places, and what each is never for.

Where each task is done

WhereWhat it is for
Novafinding and exploring data, writing SQL and notebooks, running, stopping and retrying, watching what happened
API, command line, agentseverything Nova does, and automation
Kubernetes resourceslasting settings an administrator or your GitOps tool owns: PlatformInstance, Lakehouse, Catalog, Connection, ServicePrincipal, Pipeline, StreamApp
Gitthe only way a team's work moves from dev to prod: pipelines, notebooks, SQL, stream apps
Four places to look for anything: Nova, the API, Kubernetes resources, and Git. Nova is never for anything you could not also do through the API. Kubernetes resources and Git carry lasting settings and a team's work, never runs, results or secret values.
